R / 01

长时间应用开发的
Harness 设计

长任务的关键不是让单个 Agent 一直写代码，而是把规划、实现和真实环境验收拆开，用可验证的完成标准形成反馈闭环。

  • 职责分离：Planner 定义产品目标，Generator 实现，Evaluator 独立操作应用并挑错。
  • Sprint Contract：编码前明确本轮范围、完成定义、验收行为和失败条件。
  • 上下文治理：Compaction 保留连续性；必要时通过结构化交接进行 Context Reset。
  • 真实验收：验证 UI、API 与数据副作用，而不是相信按钮、函数或完成声明已经存在。
工程边界

文章展示的是少量高成本应用案例。更完整不等于更高效，Evaluator 也可能漏测或受评分 Prompt 偏好影响。

R / 03

两条路线指向同一个结论

模型负责提出行动，Harness 负责决定行动在什么上下文、权限与验收条件下生效。可靠性来自模型外部的系统约束。

Context+Boundaries+Evidence+Recovery
  1. 01

    把“完成”写成可验证契约，不能让 Agent 自己定义成功。

  2. 02

    权限与状态迁移由业务系统掌握，Prompt 不能替代授权。

  3. 03

    保存结构化轨迹和交接产物，使长任务能够恢复、审计和复查。

  4. 04

    模型升级后重新做消融，只保留仍然创造价值的 Harness 结构。

03 / ENGINEERING PRINCIPLES

把不确定性
关进系统边界

  1. 01

    Explicit boundaries

    权限、预算与工具能力必须显式；高风险动作不能依赖模型“自觉”。

  2. 02

    Evidence over appearance

    执行完成不等于任务正确。结论、变更与验收证据需要能够关联和复查。

  3. 03

    Failure is a state

    超时、取消、中断和外部调用失败是正常状态，必须有明确语义与恢复路径。

  4. 04

    Local first, least privilege

    数据优先留在本地，能力按需开放；便利性不能成为扩大攻击面的理由。
